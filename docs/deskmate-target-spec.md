# DeskMate（桌伴）项目目标规格与开发路线

> 版本：v1.0\
> 整理日期：2026-11-18\
> 用途：作为后续分轮开发、验收、简历准备和面试学习的目标参照。\
> 状态口径：当前进度依据用户提供的 R2、R3 完成报告及 R3.1 验收反馈整理；本文未重新审查当前代码，也不代表尚未验收的能力已经完成。

## 一、项目定位与最终交付形态

**DeskMate（桌伴）——基于大模型 Agent 的桌面个人事务助手。**

面向个人学习、项目研究和日常资料管理，通过自然语言完成资料整理、文件生成和后续任务安排；结合持久任务、长期记忆与桌面通知，持续跟进用户交办的事务。

本文描述的是最终计划交付的版本。执行内核、会话服务和桌面入口已建立，R3.1 已完成并推送。R4 的资料整理流程已实现，离线回归、指定真实 Provider 任务、取消后重用及会话恢复均已验收。真实 HTTP 读取期间取消与实网重定向的覆盖限制见验证记录。R5 已实现一次性提醒、每周资料任务、持久历史与中断核对；双平台离线回归和 Windows 指定真实 Provider 主流程、成果重启检查已有证据，真实拒绝写入案例由用户跳过补做，完整覆盖边界见验证记录。R6 已实现工作区确认记忆、有界本地召回和来源管理，通过完整离线桌面流程及七项 Windows 可见人工验收；复审两项来源修复已通过双平台离线回归，真实 Provider 记忆质量仍未验收。主动通知属于 R7。

最终交付物是一款可以在明确支持的平台上安装、运行的桌面应用。

用户打开 DeskMate 后，可以直接用自然语言安排事务，例如：

> “把这几个网页和工作区里的项目笔记整理成一份复习计划，保存到本地。记住我喜欢先给结论、再列步骤。明天晚上七点提醒我继续完成剩余内容。”

DeskMate 应能够完成一条连续的处理流程：

**理解需求 → 调用工具处理资料 → 必要时请求授权或补充信息 → 生成实际文件 → 保存任务与相关记忆 → 在适当时间提醒用户 → 根据后续反馈继续处理。**

最终项目围绕三个特点建立辨识度：

- **能够办事：**通过工具处理真实资料并产生实际结果。
- **能够持续跟进：**保存事务状态，在后续时间继续执行或提醒。
- **能够利用过去的信息：**在新任务中引用相关偏好、项目事实和历史记录。

这三点共同构成 DeskMate 的产品价值，也对应后续最值得写进简历的技术工作。

## 二、主要使用场景

主要场景收敛到 **“个人资料整理与事务跟进”**，围绕这一类场景打通完整流程。

### 2.1 学习与研究资料整理

用户提供网页链接、本地笔记、项目说明等材料，DeskMate 根据要求读取、归纳和组织内容，生成摘要、学习计划或行动清单。

例如：

- 整理几篇技术文章，输出一份带来源的学习笔记。
- 根据项目文档生成阶段总结和下一步计划。
- 汇总本地材料，生成面试复习清单。
- 根据新的资料更新已有总结。

最终可见的成果应包括真实保存的文件、使用的资料来源，以及需要用户继续处理的事项。首个成熟场景可以先采用 Markdown 文件，便于验证内容、版本和输出结果。

### 2.2 个人任务安排与提醒

用户通过自然语言提出待办事项，DeskMate 将其转为可以查询和管理的任务。

例如：

- 明晚提醒复习某个知识点。
- 每周固定时间提示整理本周项目进度。
- 在资料整理任务完成后通知用户查看结果。
- 对尚未完成的事项提供继续处理、稍后提醒或取消的入口。

需要明确区分两类任务：

| 类型 | 最终行为 |
| --- | --- |
| 提醒任务 | 到达指定时间后提醒用户，等待用户处理 |
| 执行任务 | 在已授权的范围内执行指定操作，并反馈结果；需要补充信息或授权时等待用户 |

用户应能看到任务当前处于什么状态，以及失败、取消、过期后如何处理。

### 2.3 持续的项目跟进

当用户围绕同一个项目多次使用 DeskMate 时，助手可以利用相关记忆继续工作。

例如，用户之前已经确认：

- 项目的目标是什么。
- 当前推进到哪个阶段。
- 总结文档喜欢采用什么格式。
- 下一步需要关注哪些事项。

之后用户说：

> “按照我之前的格式，把这轮进展补充到项目总结中。”

DeskMate 能检索相关信息，结合本轮材料继续处理。用户也能查看这些记忆的来源，并修改或删除不准确、过时的内容。

## 三、最终版本的六个核心模块

最终功能固定为下面六个模块，与现有逐轮改造路线对应。

| 模块 | 最终应具备的能力 | 主要对应阶段 |
| --- | --- | --- |
| 桌面对话与统一执行 | 桌面输入、流式回答、工具过程展示、权限确认、补充问答、取消、新建及恢复会话；桌面与终端复用执行内核 | R1–R3.1 |
| 个人事务工作流 | 综合明确支持的网页资料与本地文件，执行多步整理任务，生成可检查的文件和来源记录 | R4 |
| 持久任务与调度 | 创建、查看、修改、取消任务；支持一次性定时及简单周期任务；保存状态并处理重启后的任务恢复 | R5 |
| 长期记忆与来源关联 | 保存必要偏好、项目事实和事务线索；按当前任务检索；支持查看、修改、删除和来源追溯 | R6 |
| 主动通知与后续交互 | 针对到期、完成、失败、待确认等事件发出通知；用户可以继续处理、稍后提醒或取消 | R7 |
| 安装分发与完整交付 | 在选定平台完成安装、启动、配置、运行和退出验证，形成演示案例、使用文档及面试学习材料 | R8 |

### 3.1 后台常驻的具体目标

窗口隐藏或最小化后，应用仍能继续消费执行事件、处理正在运行的任务，并在需要时提示用户。

应用应具有清晰的生命周期：

- 隐藏窗口时保留运行。
- 取消时结束当前请求，之后仍可继续使用。
- 退出时清理资源并结束后台线程。
- 没有系统托盘的环境提供可用的替代操作。

**程序完全退出后的任务如何处理，属于持久任务恢复策略。**最终版本需要明确记录哪些任务等待重新调度、哪些任务已经中断，以及过期任务是补做、提醒还是跳过。

### 3.2 长期记忆的具体目标

长期记忆应保存对后续任务有用的信息，并在需要时检索使用。

重点支持三类信息：

| 记忆类型 | 示例 |
| --- | --- |
| 用户偏好 | 总结格式、常用输出位置、表达习惯 |
| 项目事实 | 项目目标、当前阶段、已确认的技术决策 |
| 事务关联 | 某个任务使用了哪些资料、生成了哪个文件、还有哪些后续事项 |

需要保留来源和管理入口，让用户能够判断记忆是否可靠、是否仍然适用。明确要求保存的内容，以及经过用户确认的信息，可以作为长期记忆的主要来源。

现有工程已经有部分记忆基础；后续目标是把它完善成 **用户可感知、可管理、可验证的产品能力**。

### 3.3 跨应用关联的具体范围

第一版明确落到：**网页资料、本地文件、会话、任务、记忆和输出结果之间的关联。**

例如，某项复习任务能够追溯到原始文章、项目笔记和生成的复习计划；用户从提醒进入任务后，可以继续处理相关内容。

后续若增加浏览器或其他应用适配器，再扩展支持范围。首版验收以实际接入的信息来源和工具为准。

### 3.4 主动性的具体目标

主动行为由明确的时间、任务状态或用户授权触发，例如：

- 指定时间到了，提醒用户。
- 后台任务完成，通知用户查看结果。
- 执行需要授权，提示用户确认。
- 任务失败，说明原因并提供重试入口。
- 用户选择稍后处理，按新的时间再次提醒。

这些行为可以测试，也能让面试官清楚理解系统为什么会在某个时刻采取行动。

## 四、贯穿后续开发的完整演示案例

后续每轮都增强同一个演示案例，方便开发验收，也方便最终面试展示。

### 4.1 示例请求

> “请根据我提供的两篇文章和工作区里的项目笔记，整理一份本周复习计划，保存为 `learning-plan.md`。记住我喜欢‘结论、依据、行动项’的格式，明晚七点提醒我继续完成未完成的内容。”

### 4.2 最终应观察到的过程

1. **理解与执行。**DeskMate 识别资料整理、文件生成、偏好保存和提醒安排等需求，调用相应工具。
2. **必要交互。**按实际权限策略请求授权；遇到缺失信息时让用户补充。用户可以拒绝或取消。
3. **生成结果。**在指定工作区生成文件，内容包含整理结果、资料来源和行动项。
4. **保存任务。**将提醒及相关任务记录持久保存，关联本次输出文件。
5. **保存记忆。**保存用户明确提出的格式偏好，并能够查看、修改或删除。
6. **后续提醒。**到达时间后，在支持的运行条件下通知用户。用户可以打开任务、继续处理、稍后提醒或标记完成。
7. **跨会话继续。**用户下一次进入项目时，可以恢复相关任务和会话，并引用已有偏好继续整理资料。

这条案例能够同时展示 **Agent 执行、桌面生命周期、任务调度、记忆检索和主动交互**，也作为后续每一轮开发的验收依据。

## 五、简历与面试应围绕的工程主线

后续依据简历样例取舍表达；每条最终成果应对应实际实现与验收证据。

### 5.1 统一 Agent 执行内核与会话服务

这一部分已有明确的改造基础。核心内容包括：

- 将模型与工具执行收敛到统一循环。
- 提取无 UI 的会话服务。
- 统一执行事件、权限请求及回复关联协议。
- 让终端与桌面入口复用核心执行能力。
- 明确会话保存、恢复、取消和资源关闭的职责。

简历可以借此体现对 **系统职责划分、接口设计和执行一致性** 的理解。

### 5.2 桌面界面与异步后台的协作

这一部分是 R3 的主要工程工作。核心内容包括：

- Qt 主线程负责界面。
- 后台线程承载长期运行的 asyncio 循环。
- 应用级控制器持续消费事件。
- GUI 通过展示快照更新状态。
- 隐藏、取消、退出具有各自清晰的处理流程。

这能说明项目处理过 **线程归属、事件传递、界面响应和资源生命周期** 等具体问题。

### 5.3 持久任务的状态与恢复

这一部分是后续 R5 的主要价值。要解决的问题包括：

- 一条自然语言指令怎样变成可管理任务。
- 任务状态如何变化。
- 调度时间如何保存。
- 程序重启后怎样识别待执行、中断及过期任务。
- 失败后怎样重试，如何处理可能已经产生的操作结果。

最终简历以实现后的状态模型和恢复策略为依据。任务恢复能力需要明确到具体行为，不能笼统写成任意任务都能无损续跑。

### 5.4 可追溯的个人记忆与主动跟进

这一部分主要对应 R6、R7。核心内容包括：

- 从明确的信息中保存有用记忆。
- 根据当前任务检索相关内容。
- 建立记忆、资料、会话和任务之间的关联。
- 根据时间及任务事件生成通知。
- 接收用户的继续处理、延期或取消操作。

这条主线能够体现 **个人助手如何形成连续服务体验**，也是项目面向个人事务的重要特色。

### 5.5 技术选型口径

目前已明确的主要技术基础是 **Python、PySide6、asyncio、已有模型 Provider 适配及工具系统**。

任务存储和记忆检索的具体选型，在对应轮次确定，之后再据实补充到简历。最终目标可以用于准备简历草案，但尚未完成的能力不能直接写成已交付成果。

## 七、最终完成的判断标准

以下清单用于最终版本验收。此处未勾选，表示没有在本文中提前认定整项已经通过。

- [ ] **能够完成真实事务。**使用真实 Provider，在桌面中处理指定网页和本地资料，生成可检查的文件。
- [ ] **能够管理执行过程。**授权、拒绝、补充信息和取消等路径都有明确行为。
- [ ] **能够保存并调度任务。**任务记录在重启后仍存在，执行、中断和过期策略可以验证。
- [ ] **能够利用长期记忆。**不同会话之间可以使用相关偏好或项目事实，并支持来源查看和修改删除。
- [ ] **能够主动跟进。**在支持的运行环境下，对到期、完成和待确认事件提供可操作的提醒。
- [ ] **能够交付和讲清楚。**有可复现的安装运行方式、完整演示案例、验证记录和实现学习文档。

## 八、范围与使用约定

### 8.1 本阶段的范围

本阶段优先完成上述六个核心模块及验收目标，并以实际验收结果声明平台与功能支持范围。

通用视觉 GUI 操作、持续屏幕感知、语音交互、桌宠人格、多设备同步等，保留为后续增强方向，不默认加入当前目标版本的完成条件。

### 8.2 后续开发如何使用本文

1. 每轮开发开始前，将该轮目标对应到本文的模块、演示案例和验收标准。
2. 具体实施范围、代码修改和验证命令由当轮开发提示词及实际代码决定。
3. 每轮结束后记录已完成内容、证据、限制和剩余事项，再更新进度；区分开发完成、自动化验证和真实环境验收。
4. 随开发逐步补全路线、学习和验证文档，最终再整合演示与面试材料。
5. 如果目标范围或实现方案调整，同步更新本文，避免旧目标与实际开发脱节。

**最终项目主线：围绕个人资料整理与事务跟进，实现具有统一 Agent 内核、持久任务、可追溯记忆和主动通知能力的桌面助手。**
